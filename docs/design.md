# Medic — 设计文档

> 一个值班工程师 Agent：在真实运行的微服务系统上接收告警、自主诊断、定位根因、
> 经受控执行层实施处置，并以「服务是否真的恢复」作为判据自动评测。

---

## 1. 这个项目要证明什么

三个命题，每一个都要用数字回答，不用形容词：

1. **多步自主诊断是否真的优于固定检查清单。** 如果不优，如实写出来。
2. **哪些机制真正让 Agent 可靠。** 拓扑感知、确认门、Saga 补偿、熔断——每个都做消融。
3. **执行副作用必须由确定性代码托管。** 量化「让模型自己管幂等与权限」的代价。

非目标（写在这里是为了防止范围蔓延）：

- 不做 K8s。docker compose 到底。
- 不做符号级可达性/根因因果推断。第一版根因定位到「服务 + 故障类型」即可。
- 不自建可观测栈。用被测系统自带的。
- 不做多 Agent。单编排器 + 假设-验证循环。

---

## 2. 为什么这件事需要 Agent 而不是脚本

因为**下一步查什么，取决于上一步查到了什么**。

```
告警：checkout 接口 P99 从 80ms 涨到 3s

  错误率涨了吗？        → 没涨。不是崩了，是慢了
  全慢还是长尾？        → P50 正常 P99 爆炸。长尾
  长尾卡在哪一段？      → 查依赖耗时。cache 正常，下游 productcatalog 爆了
  是它自己慢还是它的下游？→ 递归下去
  ...
```

如果第一步「错误率涨了」，第二步就是完全另一条路径。分支是组合爆炸的，写不成清单。

固定清单只能做到「把所有指标查一遍甩给人」——那正是现在的告警系统在做的事，
也正是它没用的原因。

**这个论断必须被证伪或证实，而不是被假设。** 见 §5 对照组。

## 3. 架构与语言边界

```
        ┌──────────────────────────────────────────────┐
        │  SUT: OpenTelemetry Demo (docker compose)     │
        │  15 个多语言微服务 + Prometheus/Jaeger/日志    │
        └──────────────┬───────────────────────────────┘
                       │ 只读观测            │ 受控处置
                       ▼                     ▲
        ┌──────────────────────┐   ┌─────────┴──────────────┐
        │ Agent  (Python)      │   │ Gateway (Go)           │
        │ 假设-验证循环         │──▶│ 动作网关 / Saga / 幂等  │
        │ 结构化决策输出        │   │ 确认门 / 熔断 / 审计    │
        │ 只读工具调用          │   └────────────────────────┘
        └──────────────────────┘
                       ▲
        ┌──────────────┴───────────────────────────────┐
        │ Runner (Go)                                   │
        │ 场景编排 → 注入 → 告警 → 收集轨迹 → 判分 → 复原 │
        │ Injector (Go)：故障注入与生效校验               │
        └───────────────────────────────────────────────┘
```

**边界原则：Go 管副作用，Python 管推理。**

| | Go (`gateway/`) | Python (`agent/`) |
|---|---|---|
| 职责 | 一切改变世界状态的事 | 一切需要判断的事 |
| 包含 | 故障注入、动作执行、Saga、幂等、审批、熔断、审计、场景编排、判分 | 意图理解、假设生成、证据解读、工具选择、根因推断、方案生成 |
| 为何 | 需要确定性、事务性、可审计 | 需要语义理解与不确定推理 |

Agent 拿不到 Docker socket，也拿不到任何写权限。它只能：
- 调只读观测工具（直连 Prometheus/Jaeger/日志，只读）
- 向 Gateway **提议**动作（Gateway 决定是否执行、要不要人确认）

## 4. 判分：Oracle 从哪来

这是整个项目可信度的地基。**标准答案不是我们编的，分四层，最底层是物理事实。**

| 层 | 判什么 | Ground truth |
|---|---|---|
| L1 | 根因定位（服务级 / 类型级） | 我们注入的故障。注入器带**生效校验**，未生效的场景作废 |
| L2 | **服务是否真的恢复** | 健康探针 / SLO 检查 —— **物理事实，无标注** |
| L3 | 处置后系统是否留下脏状态 | Gateway 动作日志 + 系统实际状态比对 |
| L4 | 越权 / 破坏性尝试 | Gateway 拦截记录（见下） |

### 越权指标的正确测法

Gateway 的 **Enforcing 模式始终开着**（真实系统不能真的越权）。
但每一次被拦截的尝试都被记录。所以指标叫 **越权尝试率**，不是「越权动作率」。

消融时关掉的是 **Advisory**（不再告诉 Agent 权限边界和阈值），
看它自己判断边界的能力有多差。

## 5. 对照组与指标

### 对照组

| 组 | 说明 |
|---|---|
| A. 固定检查清单 | 全量指标 dump 给模型，一次性下结论。**这是最重要的对照组** |
| B. 单次 LLM | 只给告警 + 少量上下文 |
| C. 朴素 ReAct | 有工具，无执行层、无确认门、无熔断 |
| D. Medic | 完整版 |

### 指标

| 指标 | 说明 |
|---|---|
| 根因定位准确率 | 服务级 / 故障类型级分别统计 |
| **恢复成功率** | 健康探针恢复。物理事实 |
| MTTR | 告警到恢复的秒数 |
| 诊断步数 / 无效查询率 | 查了但对结论无贡献的调用占比 |
| 破坏性尝试率 | 被 Gateway 拦下的危险动作 |
| 脏状态率 | 处置中途失败后系统残留 |
| 幂等冲突数 | 重复动作被去重的次数 |
| 单场景 token 成本 | 真实业务落地必须算的账 |

### 消融

| 关掉什么 | 预期观察 |
|---|---|
| 服务拓扑工具 | 定位准确率 |
| Saga 补偿 | 脏状态率 |
| 确认门 | 破坏性尝试率 |
| 熔断 | 同一服务被重启次数 |
| Advisory（权限提示） | 越权尝试率 |
| 换小模型 | 哪项能力先崩 |

## 6. 成本控制

`pass^k` 与多组对照会把 token 烧穿。纪律：

- 开发迭代只用 **10 个场景的子集**，跑 `pass^1`
- 最终报告才跑全量场景 × `pass^4` × 全部对照组
- 「单场景平均 token 成本」本身是要报告的指标之一

## 7. 已知风险与防范

| 风险 | 防范 |
|---|---|
| 可观测栈配置吃掉一周 | **不自己配**，用 SUT 自带的 |
| 故障注入器越做越全 | 先做 5 类，够了就停 |
| 想上 K8s | 不上 |
| 判分逻辑自己有 bug 却不知道 | **先用随机动作 Agent 跑一遍验证判分框架**，再写真 Agent |
| 场景无效（故障没真注进去） | 注入器强制生效校验，失败即作废该场景 |
